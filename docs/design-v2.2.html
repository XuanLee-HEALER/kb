KB · 知识库系统

v2.2 design spec · delta-oriented · schema-first · MCP-native

01概览

个人知识服务。对外暴露 MCP（给 Claude Code）与 REST（给人）两个表面，底层是单台 Rust 服务 + SQLite。知识本身强类型，分类由写入时声明的 schema 决定而不是事后聚类。

这个 KB 是什么

不是知识库。是你这个具体个体相对于通用 LLM 的 delta。

LLM 已经掌握绝大部分公开世界知识。值得进 KB 的不是"OAuth 是什么"，而是 LLM 不知道或会答错的窄面：你环境的具体配置、你自己 strace 验证过的现象、kernel 5.x-foo 这个版本上 xt_TPROXY 的具体表现、你对 tokio vs smol 各维度的权重排序。这个定位决定了所有设计选择——KB 容量小、录入即固化、信噪比远比覆盖率重要。

术语 · ontology
在信息系统语境里指对一个领域里存在哪些种类的对象、它们之间存在哪些种类的关系，的一套显式声明。区别于"聚类"是从数据里事后发现结构，ontology 是事前规定结构。这个 KB 的根本决策就是选 ontology 而非聚类——五个 type 是对象的种类声明，写入时必须明确选定。

三条核心原则

  • 分类是 ontology 问题。每条知识在写入时必须声明 kind 和 natural key 字段。这不是技术决策，是认知决策——决定了你以后如何"想"这些知识。
  • 录入即固化。绝大部分 entry 写下来之后就只读。没有 Draft / Verified / Stale 这种状态机——单人 KB，你 = 审核者，写下来就是已确认。陈旧由人读到时判断，不是后台 cron 标记。
  • 关联在查询时动态产生。不存关系图。LLM 在回答"网络出问题怎么办"时通过 FTS、tag、kind 过滤把相关 entry 聚集起来，不需要预存的边。

不做什么。v2 不做自动 session 捕获、不做向量索引、不做关系图、不做状态机、不做多用户、不做 domain 受控词表。前两条是 v3+ 的事，后四条是永久不做。

02实体类型

每条记录由通用字段 + type-specific 字段组成。通用字段所有 type 共享，type-specific 字段存于 type_data JSON 列。带 ◆ 标记的字段构成 natural key，去重比较以这些字段的规范化文本为准，不比较 body。

五个 kind

Fact

NK · claim

已被验证的事实陈述，且属于 LLM 不知道或会答错的窄面。普世事实（"OAuth 流程是 X"、"tokio 是 work-stealing 调度"）不进 KB——LLM 已经会。预期是 KB 里数量最少的 kind 之一，每一条都该是干货。

claimString事实主体。一句话陈述，不带情境也成立。
evidenceVec<Evidence>至少一条。可以是命令输出（Output）、外部链接（Url）、或自验证记录（SelfVerification）。
判别规则：写之前问自己"通用 LLM 不查任何资料能不能答对这条？"。如果能 → 不要写。如果不能 → 写，并且 evidence 必须真实充分，不能只填 "我记得是"。

ProblemSolution

NK · symptoms ⊕ root_cause

具体的诊断闭环：在什么环境下遇到什么症状，根因是什么，解法是什么，怎么验证。KB 中数量可能最多的 kind——每次和 Claude Code 一起解决问题的产出大多落这里。

problemString问题陈述。一句话说清。
environmentString关键。OS、内核、运行时、版本、配置——决定问题的边界。
symptomsVec<String>外部可观测的现象。是再次定位时的检索锚点。
root_causeString根因。不是 workaround 的解释，是 why。
solutionString解法步骤。可包含命令、配置、代码片段。
verificationString?怎么证明解法成立。强烈建议填。
判别规则：绑定具体环境与具体诊断 → ProblemSolution。能从多次诊断中抽离的可迁移判断 → Lesson 或 Heuristic。同一问题在不同 environment 下分开写两条，body 互相 [[ULID]] 引用，不要合并。

Lesson

NK · trap

陷阱型经验。"很容易想到 X，但实际上是错的"——和 ProblemSolution 是正反关系：PS 说该怎么做，Lesson 说不该怎么想。在排错语境下两者价值相当。

trapString那个"很容易想到"的错误思路。这是被记住的核心，所以是唯一的 NK。
correctionString实际正确的做法或理解。不参与 NK——同一 trap 不应同时有两套 correction。
whyString为什么这个陷阱有迷惑性。给出迷惑机制，让未来读者能识别同类陷阱。
contextString?这个陷阱通常出现在什么情境。可空但强烈建议填，否则容易跨情境误用。
判别规则：陷阱型框架（"容易想到 X 但实际..."）→ Lesson；正向解决方案（"X 在 env Y 下的解法是 Z"）→ ProblemSolution。同一 trap 出现两条不同 correction 说明其中一条理解错了——supersede 一条，不要并存。

Decision

NK · context ⊕ decision

架构选择。在各种 tradeoff 与 limit 下求出的当时最优解，带"在当时上下文下成立"语义。预期固化，变动主要通过 supersede 形成演化链——这条链本身就是你的 ADR 演化史。

contextString做决策时所处的情境与约束。
decisionString最终选择。一句话说清。
rationaleString为什么选这个。
alternativesVec<Alternative>{option, why_not} 列表。
tradeoffsVec<String>显式接受的代价。
判别规则：同一 context 下做了不同 decision = supersede 关系（通过 superseded_by 字段表达，详见第 3 节），不是新条目。两个字段一起才构成 NK。

Heuristic

NK · problem_class ⊕ pattern

解决某一类问题的思维模式（工作流）。不是步骤清单（那是会过时的 Playbook，不进 KB），是"如何思考这类问题"——排查顺序、评估维度、应当问自己的问题。和 Fact 一起构成 KB 里价值最高的两类，数量不多。和 Fact 的差异在于：方法论有多种都能解决同一问题，写入时记录的是你的偏好，不是某种客观最优——这一点写入时要意识到。

problem_classString这种思维模式适用于哪一类问题。如"网络连通性诊断"、"异步运行时选型"、"性能回归定位"。
patternString思维模式本身。可以是有序排查清单、评估维度集合、决策树、应当问自己的问题列表——重点是"如何思考"，不是"如何执行"。
limitsString?已知的边界。什么时候这套思路不适用。可空但建议填。
判别规则：同一 problem_class 下可以有多个互补 Heuristic（如"分层排查" + "二分定位"），所以 problem_class 单独不够构成 NK，pattern 也参与。pattern 写成"具体要怎么做" → 是失败信号，那是 Playbook，不该进 KB。
辅助类型
Evidencestruct{ kind: EvidenceKind, content: String, captured_at: DateTime }
EvidenceKindenumOutput / Url / SelfVerification
Alternativestruct{ option: String, why_not: String }
SourceenumHuman / ClaudeCode{session_id, project, cwd} / Imported{from, original_date}

03关键操作语义

v1.1 里独立的"关系类型"和"状态机"两节合并简化为这一节。关系作为图边的概念被砍掉——知识之间的关联在查询时由 LLM 通过 FTS、tag、kind 动态聚合，不预存。唯一保留为一等公民的关联语义是 supersede，因为它影响默认查询行为。

supersede
复合写入语义

supersede 不是关系也不是状态转移，是一次原子复合写入：写入一条新 entry，同时把旧 entry 的 deprecated_at 和 superseded_by 标记上。旧 entry 不删除，但默认查询不返回。

API 形态是 kb.write 的可选参数 supersedes: Ulid?。带这个参数的写入是事务性的。

kb.write({
  kind: 'Decision',
  title: "切换 Reality 协议指纹策略",
  supersedes: '01HXY...'  // 旧 Decision 的 ULID
})

// 等价于事务里执行：
//   INSERT 新 entry
//   UPDATE old SET deprecated_at = now(), superseded_by = new.id

为什么不删除旧 entry？因为"我曾经认为 X，后来改为 Y，原因是 Z"这条信息本身就是知识——尤其对 Decision，supersede 链就是你的 ADR 演化史，删掉等于销毁推理过程。

deprecate
标记不再有效（无后继）

用于"这条 entry 不再正确，但我没有新的来取代它"的情况。设置 deprecated_at 和 deprecation_reason，superseded_by 保持 null。

kb.deprecate(id='01HXY...', reason="kernel 5.x 时代的解法，现在已无关")

deprecate 是单向操作，不提供 un-deprecate。如果想恢复，写一条新 entry 来 supersede 这条 deprecated 的。

inline reference
软关联约定

body 字段允许使用 [[ULID]] 形式引用其他 entry。这是纯文本约定，schema 不感知、不索引、不强制。Claude Code 读到 body 里有 [[ULID]] 时可以做二次 kb.get 拉取细节。

这取代了 v1.1 里 derived_from / refines / caused_by / exemplifies 这些显式关系类型。代价是反向查询（"谁引用了我"）要走 FTS：kb.search(query='01HXY...')，因为 ULID 字符串会被 FTS 索引。在 KB 规模 1000 条以内这个反向查询足够快。

默认查询行为
deprecated 隐藏

kb.search / kb.list / kb.recent 默认不返回 deprecated_at 非 null 的 entry。需要看废弃条目时显式传 include_deprecated: true。

kb.get(id) 不受此限制——直接按 ID 拿，能拿到的就拿到，状态字段返回给调用方判断。

这是 v1.1 状态机被砍后保留的唯一行为差异：不需要 Draft / Verified / Stale 三态，但需要"活跃 / 废弃"二态。这二态用 deprecated_at IS NULL 一个判定就够，不需要枚举字段。

04检索基础 · FTS

这一节是接下来"写入流程"和"检索流程"两节的基础设施。FTS5 是 SQLite 内置的全文搜索扩展，但它对中文的默认支持很差，需要换 tokenizer。这一节讲清楚：FTS5 在做什么、tokenizer 怎么选、索引和查询各自如何工作——之后第 5/6 节直接调用这套机制。

FTS5 是什么

FTS5 不是给 LIKE 加速的索引。它是一个独立的虚拟表，背后是倒排索引数据结构 + 查询语法 + 排序算法，和普通表共存，通过 rowid 关联。三件事必须拼起来才完整：tokenize（建索引）、MATCH（查询）、bm25（排序）。下面分别展开。

tokenizer 选择 · simple

SQLite 默认的 unicode61 对中文按字符切——"tokio 阻塞排查" 被切成 ["tokio", "阻", "塞", "排", "查"]。召回可以但精度很差，因为它不知道"阻塞"是个词组。必须换。

v2.1 选用 simple（wangfenjin/simple，C++ 实现，Rust 通过 libsimple crate 集成）。理由是它双模式共用同一索引，正好契合 KB 的两类使用场景。lindera-sqlite 也是合格备选，但只有单一词级模式，不如 simple 灵活。

simple_query · 召回模式
bigram 字符级，模糊容忍高

把中文按 bigram（相邻两字）切，例如"中华人民共和国" → ["中华", "华人", "人民", "民共", "共和", "和国", "国国", "国歌"]。查询"中华国歌"也能召回到"中华人民共和国国歌"，因为"中华"和"国歌"两个 bigram 都命中。

额外支持拼音匹配："zhoujielun" 能搜出"周杰伦"——是个小红利，对你不常用但白拿。

用在：第 6 节的人工 FTS 搜索通道，召回宽。

jieba_query · 精度模式
cppjieba 词级分词

同样的"中华人民共和国"被 jieba 切成 ["中华人民共和国"]（作为一个专有名词识别）。查询"中华国歌"不会过度召回到不相关条目。

用在：第 5 节 Layer 2 去重候选生成，需要精度而非召回宽度。

关键事实：索引只建一次（用 simple tokenizer 建，统一切成 bigram），simple_query() 和 jieba_query() 是两个 query 构造 SQL 函数，对同一份倒排索引做不同模式的匹配组装。不需要维护两套索引。这是 simple 相对其他方案的最大优势。

建索引时发生什么

当你 INSERT INTO entries_fts VALUES (?, ?, ?) 时，FTS5 把每个字符串字段交给 tokenizer 切成 token 流，再把每个 token 记入倒排表 token → (rowid, column, position)。simple tokenizer 对中文做 bigram，对英文按空格和标点切单词，混合文本统一处理。

FTS5 表的物理形态推荐 contentless 模式（不存原文，只存索引），通过 rowid 关联到 entries 主表。能省一半空间，并且 source of truth 永远在 entries 而不是 FTS 表里。

CREATE VIRTUAL TABLE entries_fts USING fts5(
    natural_key_text,
    title,
    body,
    tokenize = 'simple',
    content = ''     -- contentless：只存索引不存原文
);

-- entries 表加一列 fts_rowid INTEGER 关联
-- 写入时事务里 insert entries → 取 last_insert_rowid()
-- → insert entries_fts(rowid, ...) values (那个 rowid, ...)

查询时发生什么

FTS5 用 MATCH（不是 =）触发倒排查找。基本形式：

SELECT rowid, bm25(entries_fts) AS score
FROM entries_fts
WHERE entries_fts MATCH simple_query(?)   -- 或 jieba_query(?)
ORDER BY score
LIMIT 10

simple_query(text) 和 jieba_query(text) 是 libsimple 提供的 SQL 函数。它们的工作是把人类输入的自由文本转换成 FTS5 内部的查询表达式——自动处理转义、phrase 拼接、AND/OR 拼接。你不用手写 FTS5 query 语法（FTS5 原生语法有双引号、冒号、星号等特殊语义，手工拼容易出 bug）。这是 libsimple 相对裸 unicode61 的另一个红利。

bm25 排序

多条结果命中时 FTS5 用 BM25 打分。三个直觉：token 在文档里出现越多分越高（term frequency），token 在全库越罕见分越高（inverse document frequency），文档越短同样命中分越高（长度归一）。bm25() 返回的是负数，越小越相关——这样 ORDER BY score ASC 就是相关性降序。

可以加权指定列：bm25(entries_fts, 10.0, 3.0, 1.0) 表示三列权重依次 10、3、1。这对我们很关键——Layer 2 去重和人工搜索用不同权重，因为关注的列不同（去重看 NK 列，搜索看 title 和 NK 平权）。

在 KB 里的使用映射

使用场景query 函数列权重 (nk, title, body)用途
Layer 2 去重 jieba_query (10, 3, 1) 精度优先，NK 列压倒性权重
人工 FTS 搜索 simple_query (5, 5, 1) 召回宽，NK 与 title 平权

tokenize 和 normalize 必须对齐。第 5 节的规范化（normalize_nk）和这里的 tokenize 必须用同一套字符处理逻辑——比如 NFKC、大小写折叠都要做。否则规范化后的文本经过 tokenize 切出来的 token 序列和你预期的不一致，索引和查询会无声地错配。这是 FTS 全文搜索 bug 的最大来源，单元测试要专门验证这个对齐。

05写入流程

核心是三层去重流水线：精确哈希 → 字面 FTS → 语义比较。每一层的成本递增、准确度递增、覆盖的失败模式不同。三层都依赖规范化（normalize_nk）这个前置步骤——它的正确性决定整个流水线是否成立。

规范化 · normalize_nk

所有 type 的 natural key 文本都要经过统一规范化才能用于哈希、FTS 索引、嵌入。目的是把"措辞不同但语义相同"的输入收敛到同一份文本，让三层流水线行为可预测。规则按顺序应用：

  • NFKC 化：全角/半角、组合字符规范化。"Ｔｏｋｉｏ" → "Tokio"。
  • 小写折叠："Tokio" → "tokio"。
  • 空白折叠：连续空白 → 单空格，首尾 strip。
  • 不去除标点。"tokio block_in_place" 和 "tokio block in place" 是不同含义，标点在技术语境里有意义。
  • Vec 字段先 sort 再 join。如 ProblemSolution.symptoms 是 Vec<String>，要确保 ["A", "B"] 和 ["B", "A"] 哈希一致。
  • 多字段拼接用 \x1F（Unit Separator，ASCII 0x1F）。避免内容里出现常规分隔符的边界问题。

这个函数必须封装为单一入口 normalize_nk(kind, fields) -> String，所有写入路径强制走它。单元测试每条规则一例，每个 type 至少一个集成用例。

每一层的精确逻辑

Layer 1 · 精确哈希
捕捉规范化后完全相同的重复

SQL：

SELECT id, title, created_at
FROM entries
WHERE natural_key_hash = ?
  AND kind = ?
  AND deprecated_at IS NULL
LIMIT 1

三个条件缺一不可：natural_key_hash 是 BLOB 索引列做等值查询是 O(log N)；kind 防止跨 type 哈希巧合冲突，零成本；deprecated_at IS NULL 让已废弃 entry 不参与去重——你可以重写一条和已废弃 entry 内容相同的，意为"我现在认为之前的废弃判断不对，重新启用"。

命中时返回 DuplicateFound { layer: Exact, candidate_id, similarity: 1.0 }，流水线终止。

复杂度：< 1ms。无论后续怎么演化都保留——白吃的午餐。

局限：只能捕捉规范化后完全一致的重复。任何残留差异都会逃过——这是 Layer 2 存在的理由。

Layer 2 · 字面 FTS（jieba_query）
捕捉措辞略不同但实质相同

用 jieba_query 模式查询，要求精度优先而非召回宽——这是去重不是搜索，宽召回反而生噪声。

SELECT
    e.id, e.kind, e.title, e.natural_key_text,
    bm25(entries_fts, 10.0, 3.0, 1.0) AS score
FROM entries_fts
JOIN entries e ON entries_fts.rowid = e.fts_rowid
WHERE entries_fts MATCH jieba_query(?)
  AND e.kind = ?
  AND e.deprecated_at IS NULL
ORDER BY score
LIMIT 10

bm25 权重 (10.0, 3.0, 1.0) 对应 NK / title / body 三列。NK 列权重压倒——这是去重，命中 NK 比命中正文重要得多。

关键决策：Layer 2 只做召回，不做判定。不设阈值"bm25 < -X 就判为重复"——bm25 的绝对值依赖 token 数和库大小，跨数据集没有可比性。设阈值会反复踩坑。

在 v2，Layer 2 的 K 个候选直接作为 duplicates_found 返回给调用方。在 v3，Layer 3 接力做语义过滤后再返回。

复杂度：1 万条规模几毫秒，几十万条几十毫秒。不是瓶颈。

局限：字面匹配。"WireGuard 在 5.x 内核 MTU 处理" 和 "WG 在 kernel 5 上的 MTU 行为"——token 不重合就召不回。这是 Layer 3 的工作。

Layer 3 · 语义比较（v3）
在 Layer 2 候选集上做精排，不扫全库

Layer 3 不召回，只过滤。它只对 Layer 2 返回的最多 10 条候选计算 cosine 相似度。

fn layer3_filter(
    incoming_nk: &str,
    candidates: Vec<Layer2Candidate>,
    threshold: f32,   // 起步 0.85，半年后回调
) -> Vec<DuplicateCandidate> {
    let incoming_emb = embed(incoming_nk);
    candidates.into_iter()
        .map(|c| {
            let cand_emb = fetch_cached_embedding(&c.id);
            let sim = cosine(&incoming_emb, &cand_emb);
            (c, sim)
        })
        .filter(|(_, sim)| *sim >= threshold)
        .sorted_by_desc(|(_, s)| *s)
        .collect()
}

每条 entry 在写入路径上一次性计算 embedding 存到 sqlite-vec 的 vec0 列。Layer 3 直查不重复计算，只有 incoming 那一次现场算。

为什么不让 Layer 3 直接全库向量近邻搜索，三个理由：

  • 小数据集 IR 经验更可靠。KB 规模 1 万条以下，FTS5 + bm25 召回质量胜过向量搜索——后者在小数据集上容易被噪声主导。
  • 阈值随候选范围变化。10 条候选里设 0.85 是稳定的；1 万条里设 0.85 召回数量会爆炸或归零。范围越小阈值越稳。
  • 可解释性。Layer 2 召回的候选你能说"因为 tokio 这个 token 命中"，Layer 3 全库召回只能说"cosine 0.87"，调试痛苦。

嵌入只对 NK 文本算，不对 body 算。body 含大量上下文叙述会污染相似度，这是"schema 把语义搜索限制在结构化字段"的精确技术化。

duplicates_found 的处理选项

关系表砍掉之后，候选处理收敛为三个动作：

  • write_as_new：携带 proceed_token 强写，dedup='force'。适用于"我知道相似但确实是不同情境"——新 entry body 里可以用 [[ULID]] 引用相似的老 entry 说明差异。
  • update_existing：调 kb.update 覆盖已有条目的字段。适用于"这就是同一条，我有补充"。
  • supersede：调 kb.write({..., supersedes: old_id})，原子写新并废弃旧。适用于"我之前的理解错了"。

关键约束：Layer 3 的 embedding 只对 natural_key_text 计算，不对 body 计算。body 包含大量上下文叙述会污染相似度。这是"schema 把语义搜索限制在结构化字段"的精确技术化。

06检索流程

三个独立通道，Claude Code 自己根据问题决定走哪条。三个通道分开暴露的好处是每次调用的语义意图清晰，audit log 可分析。所有通道默认排除 deprecated_at IS NOT NULL 的 entry。

Token 预算约束：list 和 search 的返回永远不带 body，只给 id + kind + title + summary_line（body 第一行或自动摘要）。"看一眼列表"成本压到几百 token，"深入读"留给主动 kb.get 调用。Claude Code 拿到 body 后还可以解析其中的 [[ULID]] 内联引用做二次扩展。

每个通道的精确逻辑

结构化通道
SQL filter on entries 表，不走 FTS
SELECT id, kind, title, substr(body, 1, 120) AS summary_line
FROM entries
WHERE kind IN (?, ...)
  AND (tags LIKE '%"network/%"%' OR ...)  -- tag 前缀匹配
  AND deprecated_at IS NULL
ORDER BY updated_at DESC
LIMIT ?

tags 字段是 JSON array 存为 TEXT，前缀匹配靠 LIKE。若 tag 数量增长后 LIKE 性能不足，可以引入 entries_tags 关联表索引化——v2.1 先 LIKE，需要时再优化。

FTS 通道 · simple_query
召回宽，bm25 平权 NK 与 title
SELECT
    e.id, e.kind, e.title,
    substr(e.body, 1, 120) AS summary_line,
    bm25(entries_fts, 5.0, 5.0, 1.0) AS score
FROM entries_fts
JOIN entries e ON entries_fts.rowid = e.fts_rowid
WHERE entries_fts MATCH simple_query(?)
  AND e.deprecated_at IS NULL
ORDER BY score
LIMIT ?

注意 bm25 权重 (5, 5, 1)：和 Layer 2 去重的 (10, 3, 1) 不同。这里是搜索，用户不一定知道 NK 字段存了什么，title 命中应当和 NK 命中同等重要。body 仍低权重避免高频词噪声。

语义通道（v3）
vec0 cosine on stored embeddings
SELECT
    e.id, e.kind, e.title,
    distance
FROM entry_embeddings
JOIN entries e ON entry_embeddings.entry_id = e.id
WHERE embedding MATCH ?         -- sqlite-vec MATCH 语法
  AND e.deprecated_at IS NULL
  AND k = ?                    -- top-K
ORDER BY distance

v2.1 不实施。每条 entry 写入路径上预算 embedding，存到 vec0 列，查询时做近邻搜索。和 Layer 3 的 cosine 共用同一份 embedding，零冗余。

Claude Code 选择通道的指引

这段指引写进项目 CLAUDE.md：

  • 优先走结构化条件（kind + tag 前缀）。这是最便宜也最准的通道。文本 query 只作为辅助。
  • 当结构化条件不够、又记不清确切关键词时，单调 kb.search 只填 query，退化为纯 FTS。
  • 当 FTS 也召回不到、但确信"以前讨论过类似的"时，调 kb.semantic_search（v3）。这是 last resort。

07MCP 接口

MCP 和 REST 共享同一组 RPC 形状，后面是同一组 Rust handler。MCP 走 streamable HTTP transport（不要 stdio，stdio 是给本地单进程客户端的，你需要跨机器访问）。

相比 v1.1 砍掉了 kb.link / kb.unlink / kb.related 三个工具（关系不再是一等公民）。kb.deprecate 保留用于"废弃但无后继"场景。supersede 通过 kb.write 的可选参数实现。

kb.write(input: WriteInput) → WriteResult
默认 dedup='check'。可选 supersedes 参数原子废弃旧 entry
kb.update(id: Ulid, partial: PartialEntry) → { id, version }
version 单调递增，旧版本进 entry_history。预期罕见
kb.deprecate(id: Ulid, reason: String) → { ok }
无后继的废弃。superseded_by 保持 null
kb.get(id: Ulid, include_history?: bool) → Entry
按 ID 直拿，不受 deprecated 过滤影响
kb.search(query: SearchQuery) → SearchHit[]
结构化条件 + 可选 FTS query，默认排除 deprecated，返回不含 body
kb.semantic_search(query: String, filter?: PartialQuery) → SearchHit[]
v3 才启用；vec0 cosine on NK text
kb.recent(n?: int, since?: DateTime) → SearchHit[]
kb.stats() → { by_kind, active, deprecated, total }

WriteInput / WriteResult

kind: EntryKind tagged union with type-specific fields
title: String
body: String
tags: String[]
supersedes?: Ulid 原子复合写入：废弃旧并写入新
dedup?: 'check'|'force' default 'check'
proceed_token?: String 必填 when dedup='force'
WriteResult =
| { status: 'written', id, version: 1 }
| { status: 'duplicates_found', candidates: Candidate[], proceed_token }

08部署拓扑

本体跑在国内 Aliyun ECS，避免家用 Arch 服务器对外暴露的稳定性与网络出口问题。nginx 做 TLS 终结和 bearer token 鉴权，下游单进程 kb-server。多主机访问走公网 HTTPS（已有的 Tailscale/Headscale 网络在这一版不再是必需依赖，但你想叠加它做一层私网兜底也可以——不影响设计）。

nginx 配置要点

nginx 的工作只有三件：TLS 终结、bearer auth、限流。不要把它做厚——业务逻辑全在 kb-server。

server {
    listen 443 ssl http2;
    server_name kb.your-domain.com;

    ssl_certificate     /etc/letsencrypt/live/kb.../fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/kb.../privkey.pem;

    # /skill/* 公开下载，不需要 token
    location /skill/ {
        proxy_pass http://127.0.0.1:7890;
    }

    # 其他路径强制 bearer token
    location / {
        if ($http_authorization != "Bearer YOUR_TOKEN") {
            return 401;
        }
        proxy_pass http://127.0.0.1:7890;
        proxy_http_version 1.1;
        proxy_buffering off;     # 给 MCP streamable response 关掉
        proxy_read_timeout 300s;
    }

    # 写入限流：每秒 5 次足够，防误调爆库
    limit_req zone=kb_write burst=10 nodelay;
}

Token 在 kb-server 启动时生成（环境变量或 systemd EnvironmentFile 注入），不入库不入仓库。nginx 端硬编码即可，单用户系统不做 token rotation。需要换 token 时改 nginx config + reload，全部客户端的 mcp.json 同步更换——这是单用户运维的简单代价。

备份策略

SQLite 不能直接 cp（会破坏 WAL 一致性）。每日 cron 跑 sqlite3 kb.sqlite ".backup /tmp/kb-$(date +%F).sqlite"，然后 ossutil cp 推到 Aliyun OSS 异地保存。保留 30 天滚动 + 12 个月每月归档。OSS 标准存储费用对个人 KB 这种数据量可忽略。

家用 Arch 服务器在这版的角色

不参与 KB 服务。继续承担它原本的 Memos / Gitea 等服务。两个独立系统，互不依赖。这样 KB 服务的可用性不被你家里的网络出口波动影响。

09Skill 分发

kb-server 不只服务数据，也服务"如何最优使用本服务的指引"。通过一个独立的下载端点 GET /skill/download 派发一份 Claude Code Skill 压缩包——里面是 SKILL.md（行为指引）+ mcp.json 模板（连接配置）+ 安装说明 + 写入示例。装上这个 Skill 之后 Claude Code 在调用 KB 时自动获得最佳实践：KB-as-delta 原则、type 选择决策、检索通道使用策略、tag 命名约定，都无需在每个项目的 CLAUDE.md 手抄。

为什么 Skill 由服务派发而不是抄到每个项目 CLAUDE.md：kb-server 是 KB 行为的 source of truth——当 type 系统演化、NK 规则微调、anti-pattern 加入或退出时，Skill 跟着服务版本走。让 Claude Code 始终拿到与运行中服务匹配的 Skill 版本，比要你手动同步多份 CLAUDE.md 更可靠。

SKILL.md 内容大纲

这是 Claude Code 在每次启动时（或 skill 触发时）加载的"如何使用 KB"指南。按内容承重排序：

触发条件
何时该考虑调用 kb · 何时不调

该写：解决了非平凡问题之后；发现一个反直觉的陷阱；做了带 trade-off 的架构选择；归纳出一类问题的思维模式。

不写：通用 LLM 已知的事实；当下还在试错的 hypothesis；临时 workaround；其他项目独有而你不会再遇到的细节。

KB-as-delta 校验
写入前的一个问题

写之前问自己（或让 Claude Code 自检）："通用 LLM 不查任何资料能不能答对这条？"

能 → 不写。不能 → 写。这一条校验比所有其他规则都重要，是 KB 信噪比的总闸门。

type 选择决策
5 种 kind 的对话式 checklist

展开成 if-else 链：

  • 是被验证的客观陈述？→ Fact
  • 是"X 看似对但实际错"型的陷阱？→ Lesson
  • 是"在环境 E 下症状 S 的根因是 R，解法 Sol"型？→ ProblemSolution
  • 是带 trade-off 的架构选择？→ Decision
  • 是"如何思考这类问题"的方法论？→ Heuristic
  • 都不像 → 不要写，再想想
写入工作流
先搜后写 · 重复处理

写入前先 kb.search 看是否已有相关条目。直接 kb.write，自然走 Layer 1+2 去重。

遇到 duplicates_found 时，按场景挑动作：补充 → kb.update；不同情境 → write_as_new + body 内 [[ULID]] 引用；旧的错了 → kb.write({..., supersedes: old_id})。

检索策略
三通道按代价递增

先验明确（知道 kind 和 tag）→ kb.search 结构化条件。

关键词模糊 → kb.search(query=...)，走 simple_query FTS。

关键词回忆失败但确信"以前讨论过"→ kb.semantic_search（v3）。

tag 命名约定
路径前缀

形式 domain/specific，如 network/wireguard、rust/tokio、ops/headscale、macos/hypervisor。前缀的好处是 tags LIKE '%network/%' 可以模拟 facet 查询。

anti-pattern 清单
不要做什么
  • 不写步骤清单（那是 Playbook，会过时）
  • 不写"我打算"——先做完，验证了再写
  • body 不复述结构化字段——结构化字段是 source of truth
  • 不在 Lesson 里写正向解法（那是 ProblemSolution 的事）
  • 不为 Heuristic 写具体命令（pattern 是"如何思考"不是"如何执行"）
  • Fact 的 evidence 不能只填"我记得是"

{
  "mcpServers": {
    "kb": {
      "type": "http",
      "url": "https://kb.your-domain.com/mcp",
      "headers": {

      }

包的生成与发布

kb-server 仓库内维护一个 skill/ 目录作为源材料。CI 或 release 脚本把它打包成 kb-skill.tar.gz 放到 ECS 的静态文件目录，nginx 的 /skill/download 直接服务这个文件。SKILL.md 由人撰写（不是 LLM 自动生成），改动走 PR review——它是这个 KB 的 ontology 在使用层的具象表达，权重等同于 schema.rs。

10实施阶段

v2 schema 比 v1.1 简单不少（无关系表、无状态机、无 domain），但需要在 Week 1 多花点时间用真实知识演练，确认五个 type 真的够覆盖。前后阶段有阻塞关系：schema 不稳定不要写存储，存储不稳定不要写 HTTP。

Week 1

schema 固化 + ontology 演练

把 5 个 kind + 通用字段的 Rust 实体定义敲进 schema.rs，serde 跑通往返序列化。关键投入：拿最近三个月真实问题手写 50 条 entry——目标分布大概是 30 条 ProblemSolution、10 条 Lesson、5 条 Heuristic、3 条 Fact、2 条 Decision。如果某类一条都凑不出来，说明你对这个 kind 的判别还不清晰，回去重看类型卡。

Week 2

存储与去重

SQLite + entries 表 + entry_history 表 + entries_fts 虚拟表（tokenize = 'simple'，加载 libsimple 扩展）+ CRUD + normalize_nk + Layer 1 (hash) + Layer 2 (FTS5 with jieba_query)。MCP 表面实现核心 6 个：write / get / search / update / deprecate / recent。supersede 作为 write 的参数实现，确保事务原子性。FTS 测试重点：跑至少 10 条中英混合 entry，验证 normalize 后的文本经 simple tokenizer 切出的 token 序列符合预期。

Week 3

HTTP + UI + CLI

REST 表面 + 极简 Web UI（列表 / kind 筛选 / tag 前缀筛选 / 全文搜索 / 创建编辑 / Markdown 预览 / [[ULID]] 渲染成链接）+ kb CLI。Web UI 用 maud + htmx，不要 SPA。废弃的 entry 默认隐藏，加个 "show deprecated" 开关。

Week 4

部署、Skill、回灌

Aliyun ECS 上 systemd 起 kb-server，nginx 反代加 TLS + bearer token。打包 SKILL.md + mcp.json 模板 + examples 为 kb-skill.tar.gz，放到 ECS 静态目录暴露 /skill/download。Backfill ingester（读 ~/.claude/projects/*/*.jsonl + Claude.ai 导出，提取为初始 entry）。在常用项目装上这份 Skill，验证 Claude Code 能识别 KB-as-delta 规则——区分"这是 LLM 已知的普世知识，不写"vs"这是你环境的 delta，写"。

v2.2 明确不做：Layer 3 embedding 去重 / kb.semantic_search 通道 / 关系图可视化 / 多用户 / auto-capture hook / domain 受控词表 / 状态机 / token rotation。前两条留给 v3，其余永久不做。

11待决问题

body vs type-specific 字段的主从关系

建议：结构化字段是 source of truth，body 是放不下的额外叙述。这种更严格但写入摩擦大。反过来（body 为主、结构化字段是从 body 抽取的索引）更接近 Obsidian dataview 模式，更自由但纪律性差。v2 选前者，但你需要明确同意。

tokenizer 演化路径

v2.1 选 simple，理由见第 4 节。lindera-sqlite 是合格备选——如果未来 libsimple 维护节奏跟不上、或者你希望迁移到统一 CJK 处理（Lindera 支持日韩），可以换。tokenizer 切换的实际工作量：drop FTS 表、用新 tokenizer 重建、reindex 所有 entries——是个一次性操作，几分钟可完成。所以这个决策不是终身的，可以演化。

tag 命名约定

砍掉 domain 之后 tag 承担了双重职责（主题维度 + 技术域维度）。建议约定路径前缀：domain/specific 形式，如 network/wireguard、rust/tokio、ops/headscale。约定不在 schema 强制，靠你自己维持。如果半年后发现 tag 命名混乱，可以加一个 lint 脚本扫描非约定 tag 提示。

未来如果需要显式关系怎么办

如果 [[ULID]] 内联引用半年后被证明不够用——比如发现自己反复需要回答"哪些 Lesson 是从这条 ProblemSolution 推出来的？"——v3 可以加一张 relations 表。但加之前先记录"不够用"的具体案例至少 10 条作为硬证据。不要因为"图数据库看起来更优雅"就回退到 v1 的设计。

多用户
